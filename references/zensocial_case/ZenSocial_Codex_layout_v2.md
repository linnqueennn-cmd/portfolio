# Техническое задание Codex: интеграция ZenSocial в существующий сайт

## Входные данные и приоритеты

- Работай **в существующем репозитории портфолио**, а не создавай новую страницу с отдельной визуальной системой.
- Источник утверждённых текстов: `ZenSocial_case_text_v2.md` (**не** старый `index.html` и не предыдущий текст v1).
- Референс готовых визуальных компонентов: `index.html`, `styles.css`, `script.js`, `assets/` из пакета.
- Перед внедрением изучи уже существующую страницу кейса и её компоненты/дизайн-токены: типографику, сетку, ширину контента, обводку, радиусы, фоны и мобильные отступы. Если есть готовый компонент карточки, переиспользуй его.
- Не заменяй стили сайта на ZenSocial. **Стиль приложения оставляем только внутри отдельных продуктовых артефактов и мокапов.**

## Разметка и правила оформления ПО РАЗДЕЛАМ

### 01 / Первый экран
- Заголовок только `ZenSocial` + краткое описание из v2 + метаданные Продукт / Платформа / Моя роль / Статус.
- Композицию **двух телефонов** перенести кодом из `.hero-visual`, `.hero-phone`, `.phone`; внутри используются реальные `assets/cover_before_after.webp` и `assets/source_filters.webp`.
- Не рендерить мокапы нейросетью и не превращать композицию в одну картинку; CSS-рамки/положение/тени остаются редактируемыми.
- Окружающий заголовок, сетка, подписи и отступы должны быть от текущего сайта, без декоративного текста из старого прототипа.

### 02 / Задача + Мой вклад
- Обычные смысловые текстовые блоки текущего сайта. Никаких новых больших рекламных плашек, «слоганов» и случайных декоративных элементов.

### 03 / User Persona
- Перенести **саму карточку** `.persona-card`, `.persona-lead`, `.persona-body`, `.jtbd` из HTML-прототипа. Внутри карточки сохраняем эстетический стиль ZenSocial.
- Вставить без изменения и генерации оригинальное фото `assets/persona_anna.png` вместо инициалов/аватара.
- На мобильном фото располагается над текстом или рядом, если позволяет ширина; никогда не перекрывает контент. Весь текст и JTBD остаются читаемыми; карточка не обрезается.
- Снаружи карточки — обычная типографика и сетка сайта.
- Не показывать на странице отдельные оговорки «вымышленная персона», «не проводились интервью». Не утверждать при этом, что проводились интервью или валидация.

### 03 / CJM
- Сохранить в эстетике ZenSocial **только схему эмоционального пути** из `.mood-card`.
- **Шесть этапов** из `ZenSocial_case_text_v2.md` разместить в стандартных текстовых элементах текущего сайта (нумерованный список/существующий layout), не превращать каждый этап в отдельную рекламную карточку приложения.
- «Ключевой инсайт» — короткий выделенный текст через уже существующий стиль цитаты/акцентного блока сайта, без лишней графики.

### 04 / Продуктовые гипотезы — ВАЖНО
- **Не сплошной текст.** Три равнозначные карточки `H1`, `H2`, `H3`, расположенные **горизонтально в одну строку на широком экране**.
- Использовать **те же обводки, радиус скругления, цвет поверхности, внутренние отступы и hover-поведение**, что уже используются в карточках существующего сайта/кейсов. Не вводить новые токены оформления ради этого блока.
- В каждой карточке: индекс `H1`, короткий заголовок, абзац гипотезы. Все три карточки одинаковой визуальной высоты на десктопе.
- На планшете: если не помещаются, 2 + 1 либо один столбец; на телефоне — **одна карточка в строку**. Никакого горизонтального скролла и обрезанного текста.
- Подпись «Продуктовые гипотезы» — обычный заголовок кейса, не декоративный слоган.

### 05 / Ключевые решения
- Три лаконичных блока: заголовок + описание + мокап соответствующего экрана.
- Сохранить CSS-мокапы из прототипа и оригинальные файлы: `assets/source_filters.webp`, `assets/source_appearance.webp`, `assets/source_summary.webp` (или финальный `after_05.webp` после качественного экспорта).
- На десктопе можно чередовать расположение мокапа и текста, если такое уже встречается в кейсах сайта. На мобильном — **сначала текст, затем мокап**, чтобы не нарушать чтение.
- Стили текстов и разделов — от сайта, стилистика продукта только внутри телефона.

### 06 / Визуальная система
- Палитру `.color-system`, `.swatches` перенести кодом, без PNG. Цвета должны соответствовать исходному прототипу; не выдумывать новые.
- Подписи и основной текст — типографика сайта, не отдельная «страница в странице».

### 07 / Оптимизация онбординга 15 → 5
- Перенести сравнение оригинального `before_01.webp` … `before_15.webp` и согласованного `after_01.webp` … `after_05.webp`, используя текущие ассеты; версию «после» явно обозначить как **предложенную UX-итерацию**.
- Вместо множества крупных декоративных текстов сделать стандартный заголовок кейса, короткие подблоки «Проблемы» и «Предложенное решение», затем визуальное сравнение.
- Не выдавать прирост конверсии/активации за факт — тестирование пока не проводилось.
- Группы скриншотов должны адаптироваться: на десктопе сетка/лента в ширину контента, на телефоне допустим **отдельный локальный горизонтальный скролл галереи** с понятным индикатором или перенос карточек; **скролл не должен появляться на всей странице**.

### 08 / Результат
- Обычный текст и существующий стиль страницы кейса. Плейсхолдеры для отсутствующих скриншотов после входа в Instagram оставить как заглушки с подписями, не придумывать интерфейсы.

## ОБЯЗАТЕЛЬНО: адаптив и сохранность текущего сайта

1. Перенесённые блоки должны быть **адаптированы к дизайну сайта**, не только к исходному HTML. Сначала возьми размеры и брейкпоинты из проекта.
2. Проверь минимум **1440 px, 1024 px, 768 px, 390 px и 360 px**. Не допускай наложений, обрезания содержимого или горизонтального скролла всей страницы.
3. Телефоны масштабируются пропорционально, не выходят за контейнер, не перекрывают соседние секции; изображения внутри остаются оригинальными и не искажаются.
4. Persona и mood-chart читаемы на мобильном, при необходимости перестраиваются в один столбец.
5. Используй scoped CSS / CSS Modules или локально названные классы. **Не подключай `styles.css` из прототипа глобально**: он содержит общие стили `body`, заголовков, `.section` и пр.
6. Не изменяй другие страницы/глобальное меню; не применяй палитру ZenSocial ко всему портфолио.
7. Не генерируй никакие новые картинки и не перерисовывай существующие экраны. Ассеты `after_01.webp`…`after_05.webp` низкого разрешения, перед публикацией желательно заменить отдельными экспортами Figma.
8. После выполнения перечисли изменённые файлы и покажи результат на десктопе и телефоне.
